# Project 1 基线评测：RTX 5060 Laptop

本文在 RTX 5060 Laptop 上重复 [baseline-3060.md](baseline-3060.md) 的四个实验，
用来确认两台机器上的瓶颈是否一致。实验方法、命令和 `ncu` 的用法说明都沿用 3060
那份文档，这里只记录结果和差异。

## 结论

- **瓶颈和 3060 一致。** kernel 占 96.1% 的时间（3060：97.5%），kernel 内部的
  瓶颈同样是 FP64 运算，FP64 流水线占用率 84–85%（3060：82–85%）。
- **warp 内线程空等同样不是主要问题。** 32 个线程里平均有 28–32 个处于活跃状态
  （3060：27–32）。
- **5060 比 3060 快约 1.34 倍。** 单帧、分段、完整动画的比值都在 1.34–1.35 附近。
- **`nsys` 给出的绝对时间偏大约 10%。** 这台机器的 WSL2 里，单调时钟比 Windows
  主机的时钟快约 10%，`nsys` 用的正是这个时钟。占比不受影响。这也解释了 3060
  文档里"程序自报时间和 `nsys` 相差约 10%"的出入，见"计时问题"一节。
- **`ncu` 里有一组指标不能跨机器比。** 5060 上执行的指令总数是 3060 的约 3.3
  倍，而 FP64 指令数完全相同；IPC、Issue Slots Busy、Warp Cycles Per Issued
  Instruction 也跟着差了约 3.3 倍。原因没有查清。

## 计时问题

这台机器的 WSL2 里有三个互相对不上的时钟，读数字之前需要知道各自用的是哪个。

**测到的事实：**

- 用 `powershell.exe` 读 Windows 主机时间，同时读 WSL 里的两个时钟，间隔 100 秒
  左右：主机走了 91.12 秒，WSL 的单调时钟（`CLOCK_MONOTONIC`）走了 100.23 秒，
  WSL 的系统时钟走了 91.43 秒。也就是**单调时钟比主机快 10%**（比值 1.0999）。
- 系统时钟能跟上主机，是因为它被反复往回拨：90 秒内观察到三次，每次约 2.9 秒，
  间隔约 32 秒。`dmesg` 里也有多条 `systemd-journald: Time jumped backwards`。
- 同一次 kernel 执行，`nsys` 记录的时长是 2.778 秒，程序用 CUDA event 测得的是
  2.525 秒，比值 1.100，和上面单调时钟的偏差一致。

**对各个数字的影响：**

| 来源 | 用的时钟 | 可信程度 |
| --- | --- | --- |
| `project1 --offline` 的渲染时间（`gpu::Timer`，CUDA event） | GPU 侧 | 推断和主机时钟一致（它和 `nsys` 的比值正好是 1.10），可以直接用 |
| `project1_video` 的 `Elapsed` 和总时间（`base/common/timer.h`） | 系统时钟 | 和主机时钟一致，但每次读数可能有约 ±3 秒的台阶 |
| `nsys` 的各项时长 | 单调时钟 | 偏大约 10%；同一份报告里的占比不受影响 |
| `ps -o etimes`、`/proc/uptime` | 单调时钟 | 偏大约 10% |

`project1_video` 的 `Timer` 用的是 `std::chrono::high_resolution_clock`，在
libstdc++ 里它就是 `system_clock`。系统时钟往回拨的时候，累加的时间会突然变小：
低分辨率采样那次运行，最后一条进度是 `Elapsed=60.1s`，紧接着的总结却是
`Rendered 451 frames in 57.2 seconds`。

3060 文档里"程序自报 99.0 秒，`nsys` 跨度 108.7 秒"的出入，比值是 1.098，和这里
测到的 1.0999 几乎相同，两台机器又是同样的 WSL2 内核，很可能是同一个原因。但
我没有在 3060 那台机器上验证。如果成立，3060 文档里 `nsys` 的毫秒数也都偏大
约 10%，占比和结论不变。

单调时钟为什么会快 10%，我没有查。

### 低分辨率采样

`project1_video --width 640 --height 360 --fps 3`，451 帧。程序自报 57.2 秒，
最后一条进度是 60.1 秒，两者相差的 2.9 秒正好是一次系统时钟回拨（见"计时
问题"）。按 3060 文档的方法折算（乘以约 39.9）是 2283–2399 秒，实际 2211.9
秒，偏差 3–8%。3060 上的对应数字是 76.5 秒。

## 实验 3：逐段时间分解（Nsight Systems）

命令同 3060 文档。1280x720、2x2 抗锯齿、1 fps，共 151 帧。

下表的时长是 `nsys` 的原始读数，偏大约 10%（见"计时问题"）；占比不受影响。

| 阶段 | 累计 | 占比 | 平均每帧 | 3060 的占比 |
| --- | --- | --- | --- | --- |
| `renderMandelbrotSetKernel` | 81.98 s | 96.1% | 543 ms | 97.5% |
| 显存回传（Device-to-Host memcpy） | 0.31 s | 0.36% | 2.1 ms | 0.3% |
| 其余（`float4` 转 RGBA、写入 ffmpeg 管道等） | 3.01 s | 3.5% | 约 20 ms | 2.2% |

- 占比的分母是 `nsys` 记录的 kernel 时间跨度 85.30 秒。
- kernel 单帧耗时：最小 49 ms，中位数 584 ms，最大 918 ms（3060：91 / 752 /
  1231 ms）。
- `cudaMemcpy` 的 API 调用时间是 82.34 秒，几乎等于 kernel 时间，原因和 3060
  上一样：它在等异步启动的 kernel 跑完，真正的拷贝只有 2.1 ms。
- `fwrite` 累计 1.23 秒，中位数 4.7 ms，其中有一次调用用了 466 ms。
- 程序自报的总时间是 79.7 秒。`nsys` 的跨度 85.30 秒除以 1.10 是 77.5 秒，
  两者对得上（程序的计时还包含关闭 ffmpeg 的时间）。

kernel 累计时间的比值是 106.0 / 81.98 = 1.29，略低于实验 1 和实验 2 的 1.34。

## 实验 4：kernel 内部剖析（Nsight Compute）

命令同 3060 文档：第 20 秒和第 60 秒的帧取自 `project1_video --fps 1`，结尾帧用
`project1 --offline --width 1280 --height 720`。每帧都是 1280x720、2x2 抗锯齿，
block 16x16，grid 3600 个 block。这次三帧都正常采到，没有出现卡住的情况。

| Warp Cycles Per Issued Instruction | 151.1 | 125.2 | 151.3 | 494.4 / 392.7 / 493.0 |
| 其中等待解耦数学运算队列的周期 | 94.6 | 70.9 | 95.4 | 346.5 / 260.9 / 342.9 |

怎么读这些数字：

- **一致的部分。** FP64 流水线占用率、活跃线程数、FP64 指令数、Occupancy 都和
  3060 几乎一样。FP64 指令数完全相同，说明两台机器做的是同一份工作；3060
  文档里关于瓶颈的四条结论（FP64 是瓶颈、warp 发散损失小、约 87% 的 FP64 指令
  未融合、内存不是瓶颈）在 5060 上都成立。Occupancy 同样受寄存器限制，每个 SM
  最多放 5 个 block。
- **不一致的部分。** 表格最后五行。5060 上执行的指令总数是 3060 的 3.2–3.3
  倍，IPC、Issue Slots Busy 是约 3.3 倍，Warp Cycles Per Issued Instruction 是
  约 1/3.3。这些比例彼此吻合，但和 1.34 倍的实际速度差对不上。可能是两代架构
  （compute capability 12.0 对 8.6）生成的代码不同，也可能是计数口径不同，我
  没有查清。**这五项不要跨机器直接比。**
- **FMA 的估计上限更高（44% 对 37%）。** 仍然是 `ncu` 的估计，不是实测收益。
